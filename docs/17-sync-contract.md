# Контракт синхронизации (веб ↔ iPad)

Веб-приложение и приложение для iPad — два независимых клиента. Общего кода
у них нет и не будет: они сходятся только на **схеме PocketBase** и её REST API.

Компилятор эту связь не проверяет. Схема лежит в `pocketbase/pb_migrations/`,
а поля повторены вручную в двух местах:

| Клиент | Где описаны поля |
|--------|------------------|
| Веб | `src/lib/sync/library-sync.ts`, `src/lib/sync/book-file.ts` |
| iPad | `PBBookRecord` в `ios/Etagere/Auth/PocketBaseClient.swift` |

## Правило

**Меняете схему — правьте оба клиента в том же коммите, с префиксом `pb:`.**

Чеклист:

1. Новая миграция в `pocketbase/pb_migrations/` (только добавление полей,
   существующие не переименовывать — у клиентов разный цикл релиза).
2. Обновить веб-клиент.
3. Обновить `PBBookRecord` и, если поле нужно писать, тело `upsertBook`.
4. Дописать строку в таблицу ниже.
5. Проверить, что старая версия iOS-приложения продолжает работать: оно
   останется у пользователей на несколько недель дольше, чем задеплоенный веб.

Поле, добавленное только на одной стороне, — не ошибка, если оно осознанно
помечено в таблице как одностороннее. Ошибка — когда о нём просто забыли.

## Коллекция `books`

`ч` — читает, `п` — пишет, `—` — не использует.

| Поле | Тип | Веб | iPad | Примечание |
|------|-----|-----|------|------------|
| `user` | relation | чп | чп | владелец записи |
| `title` | text | чп | чп | |
| `author` | text | чп | чп | |
| `format` | select | чп | чп | `pdf` \| `epub` |
| `page_count` | number | чп | чп | |
| `last_page` | number | чп | чп | прогресс чтения |
| `local_id` | text | чп | чп | ключ сопоставления с локальной базой |
| `content_hash` | text | чп | чп | дедупликация, индекс `user, content_hash` |
| `reading_status` | select | чп | чп | `none` \| `want` \| `finished` |
| `size_bytes` | number | чп | чп | |
| `added_at` | text | чп | чп | ISO-8601 строкой, не датой |
| `meta_updated_at` | text | чп | чп | ISO-8601; iPad сортирует по нему |
| `collection_ids` | json | чп | **ч** | iPad читает, но никогда не пишет |
| `tags` | json | чп | — | |
| `drive_file_id` | text | чп | — | файл в Google Drive |
| `cloud_provider` | text | чп | — | диск, где лежит резервная копия файла |
| `cloud_file_id` | text | чп | — | id файла на этом диске |
| `file` | file | чп | — | загрузка файла в саму PocketBase |
| `cover` | file | чп | — | миниатюра обложки; заменяется, только если её перерисовали на устройстве |

Коллекция `library_collections` (`user`, `local_id`, `name`, `created_at`)
используется только вебом.

## Что из этого следует сегодня

Расхождение ниже — не баг, а осознанное состояние; здесь оно зафиксировано,
чтобы не выяснять его заново.

**Файлы книг не синхронизируются, только метаданные и обложки.** У каждого
клиента свой файл на своём устройстве. Веб при синхронизации файлы не качает:
полка строится из метаданных и миниатюр `cover`, а файл скачивается при
открытии книги или из пункта «Загрузить из облака». iPad пока поле `cover` не
читает — обложки там по-прежнему извлекаются из файла.

**Книга, добавленная на iPad, не имеет указателя на облачный файл.** iOS не
заполняет `cloud_provider` / `cloud_file_id` / `drive_file_id`, поэтому
`restoreMissingBookFiles` в вебе не сможет достать её файл — на вебе такая книга
появится карточкой без файла. Обратное направление работает: книга, залитая
из веба на диск, тоже приедет на iPad только метаданными.

**Чужие поля iPad не затирает.** `upsertBook` шлёт `PATCH` с частичным телом,
а PocketBase обновляет только присланные поля — `tags`, `collection_ids` и
облачные указатели переживают запись с iPad. Это важно сохранить: если когда-то
переведёте iOS на отправку полного объекта, перечисленные поля начнут
обнуляться.

**Даты — строки.** `added_at` и `meta_updated_at` объявлены как `text`, а не
`date`. Обе стороны пишут ISO-8601; сравнение идёт лексикографически, и это
работает, только пока формат одинаковый (UTC, с `Z`).
